# v0.2.1-pre SM75 Test Call

Language: [English](0.2.1-pre-testing-call.md) | [Simplified Chinese](0.2.1-pre-testing-call.zh-CN.md)

`v0.2.1-pre` is a public test release for the SM75 migration of vLLM 2080 Ti
Definitive Edition. It is a prerelease, not the stable production baseline.
The current `latest` release remains `v0.1.15`.

Release: [v0.2.1-pre](https://github.com/weicj/vLLM-2080Ti-Definitive/releases/tag/v0.2.1-pre)

This issue is the central place to collect build, correctness, CUDA Graph,
model-route, capacity, and performance evidence from real hardware. Please do
not treat a model that merely loads as a promoted deployment route.

Maintenance branch: [`release/v0.2.x`](https://github.com/weicj/vLLM-2080Ti-Definitive/tree/release/v0.2.x).
The `v0.2.1-pre` tag preserves the initial public prerelease snapshot; new
0.2.x validation fixes and profiles land on the maintenance branch. The default
branch and `v0.1.x` remain the stable CUDA 12.8 compatibility line.

## Scope

The release moves this hardware-focused fork onto one current runtime target:

| Component | `v0.2.1-pre` target |
| --- | --- |
| Upstream base | vLLM `v0.27.1` |
| CUDA ABI | `13.0` / `cu130` |
| PyTorch | `2.13.0` |
| Python | `3.12` |
| Target host | Ubuntu `26.04+`, Linux kernel `7+`, GCC/G++ `15` |
| Primary hardware | Two RTX 2080 Ti 22 GB cards, NVLink, TP=2, SM75 |

The maintained `v0.1.x` line remains the compatibility route for CUDA 12.8,
PyTorch 2.11, older kernels, and GCC 12/13/14. Those stacks are not an
install-time switch for this prerelease.

## Why Rebase to vLLM 0.27.1

The main value of `v0.2.1-pre` is not a CUDA ABI refresh. `v0.1.15` is based on
upstream vLLM `0.21.0`; if the only goal were to move from CUDA 12.8 to CUDA
13.0, we could keep that code base and port only the build files. We rebased
because the code needed by the current Qwen3.x, MTP, hybrid-attention, and
non-eager CUDA Graph routes has changed materially upstream. The dual-2080-Ti
work is therefore rebuilt on vLLM `0.27.1`, rather than accumulating more
backports on the 0.21.0-era runtime.

| Area | Stable `v0.1.15` compatibility line | `v0.2.1-pre` migration target |
| --- | --- | --- |
| Upstream/runtime base | vLLM `0.21.0`-era runtime | vLLM `v0.27.1` V1 runtime contracts |
| Environment | CUDA 12.8, PyTorch 2.11, older kernel and GCC support | CUDA 13.0, PyTorch 2.13, Python 3.12, Ubuntu 26.04+/kernel 7+/GCC 15 target |
| Model and serving integration | Retained validated routes | Current Qwen3.8-era model/runtime integration and maintained V1 serving interfaces |
| Graph and speculative execution | Retained SM75 graph policies | Current graph-capture, scheduler, speculative-decoding, and compressed-KV execution contracts |
| Attention/kernel work | Existing FlashInfer/FlashQLA/Triton integrations | Revalidated FlashInfer and FlashQLA SM75 paths, plus TurboQuant K8V4 MTP3 work on the new runtime |
| Maintenance model | More fork changes would accumulate on the older stack | Keep fork-specific SM75 changes guarded and small while following an upstream release baseline |

The rebase brings concrete upstream code that a CUDA-only port would not bring:

- **V1 scheduling and graph execution:** the unified scheduler, chunked prefill,
  prefix-cache accounting, speculative decoding, `FULL_AND_PIECEWISE`/
  piecewise CUDA Graph policy, Model Runner V2, and breakable/dynamic graphs
  are now one execution contract. This is the contract used by the shipped
  `normal` and `fast` profiles; it is not equivalent to changing the compiler
  or toolkit underneath vLLM `0.21.0`.
- **Qwen3.x and MTP model contracts:** upstream added Qwen3.5 dense/MoE model
  support, Qwen MTP loading and EAGLE3/speculator integration, GPTQ-MTP fixes,
  and multimodal ViT CUDA Graph support. These provide the current model and
  assistant-model interfaces that the Qwen3.8/Qwen3.x validation lane builds
  on.
- **Hybrid Mamba/GDN and KV-cache semantics:** upstream refactored hybrid
  attention, standardized KV-cache layout/specification, fixed Mamba alignment
  and partial-prefix-cache behavior, and made hybrid models work with
  speculative decoding. Those changes are directly relevant to Qwen3.x GDN
  routes and cannot be safely transplanted as a single environment change.
- **TurboQuant and compressed-cache correctness:** upstream added the KV-mode
  handling and the fix that reserves TurboQuant workspace before CUDA Graph
  capture. Without this class of change, the old route can capture a 5 MiB
  workspace and fail on a later 8 MiB continuation prefill.

Representative upstream changes include [Qwen3.5 model support (#50210)](https://github.com/vllm-project/vllm/pull/50210),
[Qwen3.5 full ViT CUDA Graph support (#42151)](https://github.com/vllm-project/vllm/pull/42151),
[dynamic speculative decoding with full CUDA Graphs (#45953)](https://github.com/vllm-project/vllm/pull/45953),
[hybrid KV-cache layout standardization (#44455)](https://github.com/vllm-project/vllm/pull/44455),
and [TurboQuant workspace reservation before capture (#44053)](https://github.com/vllm-project/vllm/pull/44053).
These are representative upstream changes, not a claim that every upstream
feature is automatically valid on SM75.

This is therefore an ABI, scheduler, model-contract, and kernel-integration
migration, not merely a toolkit upgrade. The fork still keeps SM75-specific
behavior explicitly guarded; it does not present those changes as upstream
vLLM behavior.

There is already a controlled indication that the migration is useful. On the
same dual-2080-Ti NVLink pair, Qwen3.8-27B-FP8, TP=2, FP16 KV, one 4K/128
request, and non-eager CUDA Graph execution, the FlashInfer + FlashQLA MTP3
route moved from `1453.46 / 60.70` to `1522.72 / 75.83` prefill/decode tok/s
when comparing `v0.1.15` with `v0.2.1-pre`. The corresponding noMTP comparison
was `1420.07 / 30.01` versus `1570.57 / 30.01`. Full method, graph modes, and
quality results are recorded in the
[migration validation report](2080ti-0.2.1-pre-validation.md).

These figures are evidence for a specific, controlled route, not a claim that
every checkpoint or quantization route is faster after rebasing. Every profile
still needs its own quality probe, non-eager CUDA Graph capture/replay,
capacity, and 4K/128 validation. `v0.1.15` remains the supported stable choice
for the older CUDA 12.8 / PyTorch 2.11 environment.

## What Changed

### Upstream migration and SM75 build

- Rebased the fork on upstream vLLM `v0.27.1` and the CUDA 13.0 / PyTorch 2.13
  dependency stack.
- Added a target-aware build route that creates an isolated `.venv`, compiles
  the requested SM75 architecture, records build logs, and fails closed when
  the host does not meet the target compiler, kernel, or CUDA requirements.
- Restores the `v0.1.x` resource-aware build parallelism policy: `build.sh`
  selects a safe default from CPU threads, system memory, and the configurable
  `BUILD_AUTO_MAX_JOBS_CAP` (default `8`). `MAX_JOBS` and `BUILD_MAX_JOBS`
  remain explicit user overrides.
- Preserves launcher, route-profile, validation, and benchmark evidence needed
  to reproduce the dual-2080-Ti stack.

### Non-eager SM75 serving path

- Restores the SM75 FlashInfer capability and priority path after validating
  native paged prefill/decode for the target Qwen checkpoint.
- Keeps the FlashQLA legacy forward extension for GDN prefill, with the
  Triton/FLA fallback for unsupported varlen calls.
- Validates CUDA Graph capture with `enforce_eager=False`; eager mode is a
  debug fallback and is not a deployment performance route.
- Documents mixed-GPU host selection: set `CUDA_DEVICE_ORDER=PCI_BUS_ID`
  before choosing physical GPU IDs.

### Quantization, MTP, and correctness work

- Validates SM75 Marlin weight-only paths for FP8, INT4, and the generated
  NVFP4 subset.
- Restores the fused B=4 compressed-cache decode used by TurboQuant K8V4 MTP3
  candidates. Ordinary continuation prefills keep raw-K/V merging; the SM75
  raw-K/V B=4 graph variant remains unpromoted because it can fault during
  capture.
- Covers GDN state slot zero and padded slots, Mamba alignment/external-hit
  resume behavior, and CPU KV offload store/load and partial-hit scheduling
  regressions.
- Includes the launcher, profile validation tooling, and dedicated Gemma4 SM75
  support notes.

## Known Limits and Open Work

1. **MXFP4 is not supported on SM75.** Upstream MXFP4-specific Marlin kernels
   are generated only for newer architectures. A generic FP4 capability check
   is not evidence that the SM75 MXFP4 kernels exist.
2. **TurboQuant K8V4 is checkpoint-dependent.** The current Unsloth Qwen3.8
   NVFP4 pure-text profile passed its quality gate and is recorded above. Older
   candidate checkpoints and multimodal/FP16-KV combinations still require
   separate quality validation and must not inherit that result automatically.
3. **Qwen3.6 GPTQ-Marlin MTP3 may OOM at `gpu_memory_utilization=0.96`.** A
   lower-utilization engineering run can execute, but it has not passed every
   quality gate.
4. **Qwen3.x 35B FP8 records are retained v0.1.x evidence.** They need a
   separate CUDA 13.0 revalidation before becoming `v0.2.1-pre` presets.
5. **Gemma4 has baseline support only.** Gemma4 MTP, assistant checkpoints,
   multimodal routes, capacity, and CUDA Graph behavior are not promoted SM75
   deployment routes. See the [Gemma4 SM75 support notes](gemma4-sm75-support.md).

## How To Test

Fetch the 0.2.x maintenance branch rather than assuming that it is the default
branch. The `v0.2.1-pre` tag remains available when the initial snapshot is
specifically required:

```bash
git clone https://github.com/weicj/vLLM-2080Ti-Definitive.git
cd vLLM-2080Ti-Definitive
git fetch origin release/v0.2.x
git switch --track origin/release/v0.2.x

./build.sh
```

`build.sh` automatically selects its default parallelism. Only set `MAX_JOBS`
or `BUILD_MAX_JOBS` after considering the CPU and memory available to the build
host; an explicit value overrides the automatic choice.

For a non-interactive dual-GPU launch, choose the physical 2080 Ti IDs on your
own host. The values below are examples only:

```bash
CUDA_DEVICE_ORDER=PCI_BUS_ID \
MODEL_DIR=/path/to/checkpoint \
PROFILE=qwen27b/fast/fp8/fp16kv-112K-mtp3-text-only.env \
MODE=fast GPU_DEVICES=0,1 TP_SIZE=2 \
NON_INTERACTIVE=1 ./launcher.sh
```

Run `./launcher.sh --print-config` before a benchmark if you override a
profile. Keep `enforce_eager=False` for performance and CUDA Graph validation.

## Requested Test Coverage

### Build and environment

- CUDA 13.0 / PyTorch 2.13 builds on the target host.
- SM75 Marlin extension generation and load behavior.
- Build failures, compiler/kernel/toolkit diagnostics, build duration, memory
  pressure, and the automatically selected or explicitly overridden job count.

### Serving and correctness

- Launcher startup, health check, `/v1/models`, and repeated-request stability.
- CUDA Graph capture and replay, including illegal-address, graph-replay,
  workspace, and OOM failures.
- noMTP and MTP3 output quality: repetition, gibberish, premature stopping,
  hidden-thought-only responses, reasoning parsing, and tool calling.
- Long-context, multi-turn, and multimodal cases. Report the actual usable
  context length rather than only the configured maximum.

### Model and KV routes

- Qwen3.8 FP8, NVFP4, and INT8 W8A8. The cyankiwi AWQ-INT4 checkpoint is
  excluded because its quantization metadata and tokenizer are incomplete for
  the shipped routes.
- FP16 KV, INT8 KV, and TurboQuant K8V4, each tested separately with noMTP and
  MTP3 where applicable.
- Qwen3.x 35B FP8, Qwen3.6 GPTQ-Marlin, and Gemma4 as separate experimental
  lanes with their exact model metadata.

### Performance method

The correctness probe should use a short request with thinking disabled via
the request's chat-template kwargs (`{"enable_thinking":false}`), so a small
quality budget is not consumed entirely by hidden reasoning. This does not
change the serving profile or launcher configuration. The reference short
benchmark shape is one request with a synthetic prompt of
exactly 4096 tokens after tokenization and `max_tokens=128`. It uses TP=2,
three independent measured requests, and non-eager CUDA Graph execution. This
is a token shape, not 4096 characters or a fixed natural-language prompt.

For comparable results, report whether the reference shape was used, then give
the model and weight format, KV dtype, MTP setting, profile/mode, request
concurrency, CUDA Graph mode, and three independent measurements. Please
report prefill tok/s, decode tok/s, peak memory, and MTP acceptance rate
separately. A single total-speed figure is not enough.
