## Current merge guidance

The safe 0.2.x migration set now includes #125, #128, #129, #130, #132, and #133 as current-architecture migrations or absorbed behavior; #134 is already present as a native equivalent. The launcher-only portion of #120 is suitable for pre3, but its PP runtime combinations are not promoted. #71 remains suitable for continued validation because its SM75 FP8 format selection is implemented, while its long-context quality claim still requires target-GPU evidence. #78 is wired into the 0.2.x metadata and mixed-batch paths without forward-time FlashInfer planning, but remains an experimental performance route until the target-GPU A/B is complete. #72 remains a deployment design reference rather than a code cherry-pick.

For the complete `v0.1.17` delta, the release decision is therefore:

- **Include as 0.2.x implementations:** #125, #129, #132, and #133.
- **Keep the newer native behavior; do not cherry-pick legacy code:** #128 and #130.
- **Do not duplicate an existing equivalent:** #134.

This preserves every user-visible or correctness requirement introduced by
`v0.1.17` without importing obsolete 0.1.x parser, sampling, cache, or
offloading internals into the vLLM 0.27.1 architecture.

## Validation boundary

The parser, serving, TurboQuant planning, and offload regressions are CPU-testable
architecture checks. CUDA claims remain route-specific. Pre3 separately passed
the documented CUDA 13/PyTorch 2.13 dual-RTX-2080-Ti true-concurrency run and
the packed-varlen FlashQLA numerical probe; this does not promote untested
TurboQuant long-context, PP, PP+MTP, or Gemma4 combinations.
