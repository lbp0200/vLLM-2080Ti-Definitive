# 0.2.1-pre SM75 Migration Validation

This branch ports the 2080 Ti fork onto upstream vLLM `v0.27.1`. It is an
isolated validation branch and must not be promoted as a release until every
SM75 gate below has evidence from a dual RTX 2080 Ti NVLink host.

## Target runtime

`0.2.1-pre` follows the current upstream runtime as one coherent target:

| Component | Target |
| --- | --- |
| Upstream base | vLLM `v0.27.1` |
| CUDA ABI | `13.0` / `cu130` |
| PyTorch | `2.13.0` |
| Python | `3.12` |
| Target host | Ubuntu `26.04+`, Linux kernel `7+`, GCC/G++ `15` |
| Official upstream Docker base | CUDA `13.0.3`, Ubuntu `22.04` |

Upstream `v0.27.1` pins `torch==2.13.0`. The Ubuntu 22.04 value above describes
the official upstream container build base; the target validation host is
Ubuntu 26.04 or later with Linux kernel 7 or later and GCC/G++ 15. The existing
`v0.1.x` release line remains the maintained compatibility route for CUDA 12.8
and Torch 2.11, with GCC 12/13/14 and older kernels validated independently.
That compatibility is branch-level and is not an install-time toggle in this
pre-release.

## Build entry

From this workspace, the target build is:

```bash
MAX_JOBS=24 ./build.sh
```

The script creates `.venv`, selects the CUDA 13.0 Torch backend, compiles only
the requested SM75 architecture, and records the build output under
`build-logs/`. It fails closed when the host compiler, kernel, or CUDA toolkit
does not match the target. For a non-target compile smoke only, set
`ALLOW_HOST_MISMATCH=1`; that result is not validation evidence.

## Included upstream behavior to verify

The upstream code has evolved the same areas as local PR #91 and #93:

- CPU KV offload and Mamba align external-hit handling.
- GDN/Mamba padded-state handling with `PAD_SLOT_ID=-1`.

The local PR patches must be ported only when their exact regression tests
still fail on this tree. Do not blindly cherry-pick them: their original
context conflicts with the newer upstream scheduler and offloading APIs.

## Required validation

1. Build on the CUDA 13.0 target host with `TORCH_CUDA_ARCH_LIST=7.5`.
2. Confirm the resulting extension contains and loads SM75 Marlin kernels.
3. Run PR #93's GDN slot-zero regression on CUDA, including padded slots.
4. Run the upstream CPU KV offload and Mamba-align external-hit regression
   tests. The TP=2 end-to-end run below separately validates the runtime path.
5. Run Qwen3.8-27B-FP8 TP=2 on the NVLink 2080 Ti pair: 4K/128, noMTP and
   MTP3, preserving the benchmark method used by the shipped profiles.
6. Run TurboQuant K8V4 and compare prefill/decode against the current validated
   `v0.1.x` baseline. No profile is promoted on a smoke result alone.
7. Validate MXFP4 separately: upstream's generic SM75 Marlin build does not by
   itself prove that the MXFP4 SM75 kernel variants are generated.

## Current SM75 CUDA Graph result

The CUDA 13.0 / Torch 2.13 environment has been exercised on the dual RTX
2080 Ti NVLink pair with the official `Qwen3.8-27B-FP8` checkpoint. Every run
sets `CUDA_DEVICE_ORDER=PCI_BUS_ID` before `CUDA_VISIBLE_DEVICES=4,5`: without
that ordering CUDA maps `4,5` to the two 16 GB T10s on this mixed-GPU host.
The GPU snapshots in each result show both physical 22 GB 2080 Ti devices
active and all T10s idle.

The benchmark uses TP=2, FP8 weights through the SM75 Marlin weight-only path,
FP16 compute and KV cache, `max_model_len=8192`,
`max_num_batched_tokens=8192`, one request, a synthetic 4096-token prompt, and
128 generated tokens. Every row is a fresh run with three measured requests,
`enforce_eager=False`, and `PROFILE_OK` from the 256/16 quality probe. Prefill
is prompt tokens per TTFT, decode is generated tokens per decode interval, and
wall is generated tokens per end-to-end wall second.

The comparison fixes the physical host, GPU pair, model, TP size, precision,
and request settings. `0.1.15` uses CUDA 12.8 / Torch 2.11; `0.2.1-pre` uses
CUDA 13.0 / Torch 2.13. It therefore measures the complete runtime migration,
not an assumed-equivalent CUDA stack.

| Route | Actual CUDA Graph mode | Prefill tok/s | Decode tok/s | Wall tok/s | Quality |
| --- | --- | ---: | ---: | ---: | --- |
| 0.1.15 FlashInfer + FlashQLA noMTP | `FULL_AND_PIECEWISE`, full decode capture, size 1 | 1420.07 | 30.015 | 17.776 | `PROFILE_OK` |
| 0.2.1-pre FlashInfer + FlashQLA noMTP | `FULL_AND_PIECEWISE`, full decode capture, size 1 | 1570.57 | 30.014 | 18.551 | `PROFILE_OK` |
| 0.1.15 FlashInfer + FlashQLA MTP3 | `PIECEWISE`, capture size 4 | 1453.46 | 60.702 | 25.713 | `PROFILE_OK` |
| 0.2.1-pre FlashInfer + FlashQLA MTP3 | `PIECEWISE`, capture size 4 | 1522.72 | 75.827 | 28.920 | `PROFILE_OK` |

For noMTP, `0.2.1-pre` improves prefill by 10.60% and wall throughput by
4.36%; decode is effectively unchanged at 30.01 tok/s. For MTP3, it improves
prefill by 4.77%, decode by 24.92%, and wall throughput by 12.47%. MTP3 raises
decode from 30.01 to 60.70 tok/s on `0.1.15` and from 30.01 to 75.83 tok/s on
`0.2.1-pre`.

noMTP captures a full decode CUDA Graph. With FlashInfer and speculative
decoding, both vLLM versions currently report that
`FULL_AND_PIECEWISE` is unsupported and automatically select `PIECEWISE`; they
then capture the mixed prefill/decode graph at size 4. This is a CUDA Graph
path, not eager mode, but it is not a full speculative-decode graph.

Earlier 8-9 tok/s noMTP and roughly 23 tok/s MTP3 figures were obtained with
`enforce_eager=True`. That global setting disables CUDA Graph despite any
per-run compilation configuration, so those figures are retained only as eager
debug diagnostics and are not deployment or migration results.

The upstream `v0.27.1` FlashInfer capability guard rejects SM75 because of a
known upstream issue. This fork restores the SM75 capability and priority
after validating the native FlashInfer paged prefill/decode path on the target
checkpoint. GDN prefill uses the optional forward-only FlashQLA legacy
extension; unsupported varlen calls retain the Triton/FLA fallback.

The raw benchmark JSON files are retained on the validation host under
`/mnt/ai-cache/report/vllm021-vs-0115-qwen38-4k128/`.

## TurboQuant K8V4 probe

The same Qwen3.8-27B-FP8 checkpoint was measured on superserver with the
physical RTX 2080 Ti pair (`CUDA_DEVICE_ORDER=PCI_BUS_ID
CUDA_VISIBLE_DEVICES=4,5`), TP=2, FP8 Marlin weights, FP16 compute, and
`--kv-cache-dtype turboquant_k8v4`. Attention backend selection was left on
`auto`, which selects TurboQuant attention; forcing FlashInfer is invalid for
this KV-cache dtype. Each route used the shipped `fast` values
`max_model_len=262144`, `gpu_memory_utilization=0.96`,
`max_num_batched_tokens=2560`, and `max_num_seqs=1`, with a synthetic 4096
token prompt, 128 generated tokens, three measured requests, and a 256/16
quality probe. Prefill is prompt tokens per TTFT, decode is generated tokens
per decode interval, and wall is generated tokens per end-to-end wall second.

| Route | Actual CUDA Graph mode | Prefill tok/s | Decode tok/s | Wall tok/s | Quality |
| --- | --- | ---: | ---: | ---: | --- |
| 0.1.15 noMTP | `FULL_AND_PIECEWISE`, full decode, size 1 | 1438.45 | 27.49 | 16.96 | `PROFILE_OK` |
| 0.2.1-pre noMTP | `FULL_AND_PIECEWISE`, full decode, size 1 | 1314.33 | 29.47 | 17.10 | `PROFILE_OK` |
| 0.1.15 MTP3, stock | `PIECEWISE`, size 4 | N/A | N/A | N/A | failed |
| 0.1.15 MTP3, workspace workaround* | `PIECEWISE`, size 4 | 1391.25 | 46.09 | 22.12 | `PROFILE_OK` |
| 0.2.1-pre MTP3 | `FULL_AND_PIECEWISE`, mixed piecewise + full decode, size 4 | 1272.29 | 59.39 | 23.68 | quality probe failed** |

The stock 0.1.15 TQK8V4 MTP3 route fails on the first 4K request after graph
capture: its locked workspace is 5.00 MiB, while TurboQuant continuation
prefill requests 8.12 MiB. This is a real functional defect, not a throughput
result. For the starred row only, the existing
`VLLM_TURBOQUANT_CONTINUATION_WORKSPACE_RESERVE_TOKENS=262144` environment
switch was set before startup; it reserves 512 MiB per GPU before graph
capture and leaves all model/profile arguments unchanged. It is included to
provide an engineering comparison, but is not a stock 0.1.15 result.

Against 0.1.15, 0.2.1-pre noMTP changes prefill by -8.63%, decode by +7.22%,
and wall throughput by +0.83%. Comparing MTP3 with the workspace workaround,
0.2.1-pre changes prefill by -8.55%, decode by +28.85%, and wall throughput by
+7.07%. The MTP3 0.2.1-pre synthetic requests completed, but its fixed quality
probe did not emit `PROFILE_OK` (the returned sample was repeated `Hello`
text); therefore this route is measured evidence, not a promoted quality
route, until the output behavior is investigated.

The 0.1.15 MTP3 route automatically downgrades speculative TurboQuant capture
to `PIECEWISE` because its GDN/Mamba KV-cache path does not support
`FULL_AND_PIECEWISE`. In contrast, 0.2.1-pre captured both mixed
prefill/decode `PIECEWISE` and decode `FULL` graphs at size 4. Raw JSON and
logs are retained on superserver under
`/mnt/ai-cache/report/vllm021-vs-0115-qwen38-4k128/`.

### Historical Qwen3.6 27B GPTQ comparison

This is a migration comparison against the retained `v0.1.x` INT4 route, not
an additional `0.2.1-pre` tested-checkpoint entry. The current checkpoint list
is intentionally limited to the Qwen3.8 candidates and Qwen3.x 35B FP8 records
listed in the root README. These rows remain here because they explain the
TurboQuant and Marlin regressions that still need closure before promotion.

The same TQK8V4 fast test was run against the local
`Qwen3.6-27B-uncensored-heretic-v2-Native-MTP-Preserved-GPTQ-Int4` checkpoint
(18.22 GiB). The launcher quantization is explicitly `gptq_marlin`; v0.27.1
normalizes that name to `auto_gptq` internally and logs
`Using MarlinLinearKernel for AutoGPTQLinearMethod`. Both versions use the
same physical 2080 Ti pair, TP=2, 262144-token limit, and 4K/128 three-run
method as the FP8 result above.

| Checkpoint and route | Actual CUDA Graph mode | Prefill tok/s | Decode tok/s | Wall tok/s | Quality |
| --- | --- | ---: | ---: | ---: | --- |
| Qwen3.8-27B-FP8, noMTP | `FULL_AND_PIECEWISE`, full decode, size 1 | 1314.33 | 29.47 | 17.10 | `PROFILE_OK` |
| Qwen3.6-27B-GPTQ-Marlin, noMTP | `FULL_AND_PIECEWISE`, full decode, sizes 1/2 | 1504.97 | 44.74 | 22.83 | `PROFILE_OK` |
| Qwen3.8-27B-FP8, MTP3 | `FULL_AND_PIECEWISE`, mixed piecewise + full decode, size 4 | 1272.29 | 59.39 | 23.68 | quality probe failed |
| Qwen3.6-27B-GPTQ-Marlin, MTP3, 0.1.15 stock | `PIECEWISE`, size 4 | N/A | N/A | N/A | workspace failure |
| Qwen3.6-27B-GPTQ-Marlin, MTP3, 0.1.15 workaround* | `PIECEWISE`, size 4 | 1699.44 | 56.30 | 26.95 | `PROFILE_OK` |
| Qwen3.6-27B-GPTQ-Marlin, MTP3, 0.2.1-pre stock | `FULL_AND_PIECEWISE`, mixed piecewise + full decode, size 4 | N/A | N/A | N/A | OOM |
| Qwen3.6-27B-GPTQ-Marlin, MTP3, 0.2.1-pre u90** | `FULL_AND_PIECEWISE`, mixed piecewise + full decode, size 4 | 1454.28 | 76.37 | 28.32 | quality probe failed |

Relative to the Qwen3.8 FP8 checkpoint on 0.2.1-pre, Qwen3.6 GPTQ-Marlin
improves noMTP prefill, decode, and wall throughput by 14.50%, 51.81%, and
33.48%. The u90 MTP3 engineering measurement is 14.30%, 28.60%, and 19.59%
faster, respectively. Against the validated 0.1.15 noMTP baseline, 0.2.1-pre
changes prefill by -10.13%, decode by +8.76%, and wall throughput by -0.03%.
Against the 0.1.15 MTP3 workspace workaround, the u90 measurement changes
prefill by -14.43%, decode by +35.65%, and wall throughput by +5.07%.

The stock 0.1.15 MTP3 row reproduces the locked TurboQuant workspace defect:
the first continuation-prefill request needs 8.12 MiB while the workspace is
locked at 5.00 MiB. The starred row sets
`VLLM_TURBOQUANT_CONTINUATION_WORKSPACE_RESERVE_TOKENS=262144` before startup;
it is an engineering comparison, not a stock result.

The stock 0.2.1-pre MTP3 row keeps the shipped `gpu_memory_utilization=0.96`.
Its profiling allocates 11.16 GiB of KV cache after estimating only 0.29 GiB
of peak activation. The first GDN continuation then needs another 30 MiB and
the device has only 22.9 MiB free, producing OOM (a secondary Marlin
`aten::empty` error is emitted during worker teardown). A 0.95 trial still
failed when the continuation SDPA requested 288 MiB. The double-star row uses
`gpu_memory_utilization=0.90` only to establish that the Marlin MTP3 path can
execute; its synthetic requests completed under CUDA Graph, but the fixed
quality probe returned only six hidden-thought tokens and no `PROFILE_OK`.
Neither MTP3 measurement is a release-promotion claim until both the memory
budget and output behavior are fixed.

The raw exact-Marlin reports are retained on superserver under
`/mnt/ai-cache/report/vllm021-vs-0115-qwen36-gptqmarlin-4k128/`:
`v015-nomtp.json`, `v015-mtp3.log`, `v015-mtp3-workaround.json`,
`v021-nomtp.json`, `v021-mtp3.log`, and `v021-mtp3-u90.json`.

### TQK8V4 MTP3 full-graph repair

The earlier `0.2.1-pre` TQK8V4 MTP3 number above is not the final fast route.
Its speculative full-graph dispatch used the raw-K/V prefix-merge path. On
SM75, a graph-captured B=4 prefix merge either faults during capture or falls
back to four B=1 launches, which explains the large decode regression. The
repair keeps raw-K/V merging for ordinary continuation prefills but restores
the historical fused B=4 compressed-cache decode for MTP candidates.

The repaired route was re-run on superserver with the same Qwen3.6-27B GPTQ
checkpoint, dual RTX 2080 Ti NVLink pair, TP=2, `turboquant_k8v4`, MTP3,
synthetic 4096/128 requests, and streaming TTFT-split timing:

| Route | CUDA Graph | Prefill tok/s | Decode tok/s | Wall tok/s | Output |
| --- | --- | ---: | ---: | ---: | --- |
| v0.1.14 fast baseline | `FULL_AND_PIECEWISE`, FULL size 4 | 1719.54 | 97.49 | 34.64 | 128/128 filler tokens |
| v0.2.1-pre repaired fast | `FULL_AND_PIECEWISE`, PIECEWISE + FULL size 4 | 1755.29 | 107.17 | 36.20 | 128/128 filler tokens |

The three repaired measurements were `106.40`, `107.17`, and `108.21`
tok/s. The launcher diagnostics show `FORCE_DECODE_SDPA=0`, GDN FlashQLA
legacy, and TurboQuant FlashInfer FA2; `enforce_eager` remains false. The
raw-K/V B=4 graph variant is not promoted on SM75 because it still triggers
the illegal-address failure observed in the pre-repair log.

## MXFP4 on SM75

The current upstream Marlin integration does not provide an SM75 MXFP4 route.
The CUDA target list in `CMakeLists.txt` restricts MXFP4-specific targets to
SM100/SM110/SM120, and a direct `generate_kernels.py 7.5` run emits no
`BF16 + FP4 + E8M0` MXFP4 kernel. The generic
`is_fp4_marlin_supported()` capability check returning true for SM75 is not
evidence that those variants exist. SM75 remains validated for Marlin FP8 and
the generated FP16/INT4/NVFP4 subsets, but MXFP4 would require a new SM75
kernel, E8M0 scale handling, and selector coverage before it can be claimed.

On superserver, the source build completed with `MAX_JOBS=24`, followed by the
launcher using the official checkpoint, `GPU_DEVICES=4,5`, and TP=2. The smoke
route used an 8192-token temporary limit and MTP=0 to isolate startup:

```bash
MODEL_DIR=/mnt/ai-cache/data/max/models-vllm/Qwen3.8-27B-FP8 \
PROFILE=qwen27b/fast/fp8/fp16kv-112K-mtp3-text-only.env MODE=fast \

MAX_BATCHED_TOKENS=8192 MTP_K=0 SERVED_NAME=qwen38-launcher-smoke \
NON_INTERACTIVE=1 ./launcher.sh
```

The run returned `START OK`, `Health check: OK`, and `Smoke response: OK`;
`/v1/models` reported `qwen38-launcher-smoke`. The service was stopped after
the check to release the two validation GPUs.
