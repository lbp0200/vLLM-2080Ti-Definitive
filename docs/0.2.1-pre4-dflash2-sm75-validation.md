# DFlash2 SM75 Validation Notes

Status: experimental. These results do not promote DFlash2 into a release
profile. The frozen pre4 baseline is `315d5930` (`v0.2.1-pre4`).

The long-context candidate is
`2x2080Ti/qwen27b/w4a16/fast/dflash2-tqk8v4-2x172k-text-only.env`. It relies on
the native DFlash2 KV-pool layout, which keeps the five FP16 draft pages
separate from the aligned TurboQuant target pages. It still requires an SM75
startup and long-prompt validation before promotion.

## Test Setup

- Host: `192.168.1.31`
- Physical GPUs: RTX 2080 Ti at PCI `05:00.0` and `0B:00.0`
- Selection: `CUDA_DEVICE_ORDER=PCI_BUS_ID`, `GPU_DEVICES=1,5`, TP=2
- Target: `Qwen3.8-27B-NVFP4`, compressed tensors, target KV
  `turboquant_k8v4`
- Draft: `Qwen3.8-27B-DFlash2`, FP16 draft KV, seven draft tokens
- Verifier graph: full plus piecewise, capture width B=8
- Target prefill: tree-local FlashQLA SM70/SM75 legacy GDN extension

The complete FlashQLA dependency is intentionally local to the experimental
runtime at `.deps/FlashQLA-SM70-SM75`; it is ignored by git and is not bundled
in the lean fork.

The streaming benchmark excludes one warmup and reports:

- prefill tok/s = input tokens / TTFT
- decode tok/s = (output tokens - 1) / (last token time - first token time)
- E2E total tok/s = (input tokens + output tokens) / full request wall time

## High-Acceptance 4K/128 Results

The synthetic prompt is exactly 4096 repeated `alpha` tokens. Every timed run
returned 128 tokens. The raw DFlash acceptance count was 111/111 (100%).

| Route | Timed runs | Prefill tok/s | Decode tok/s | E2E total tok/s |
| --- | ---: | ---: | ---: | ---: |
| FP16 target KV | 2 | 1477.5 | 132.8 | 1132.8 |
| TQ K8V4, default tile=2 | 2 | 1484.8 | 187.9 | 1229.9 |
| TQ K8V4, max KV splits=8 | 4 | 1477.9 | 187.0 | 1224.1 |
| TQ K8V4, tile=4 | 4 | 1473.6 | 190.8 | 1226.0 |
| TQ K8V4, tile=8 | 4 | 1476.7 | 189.4 | 1226.6 |
| TQ K8V4, tile=4, stage-1 warps=2 | 4 | 1479.8 | 182.9 | 1219.9 |

Tile=4 is a small, measured improvement over tile=2 but remains below the
isolated decode gate of 200 tok/s. It is not enabled in the profile.

The stage-1 warp=2 run used the same actual 4096/128 request, 111/111 (100%)
acceptance, RTX 2080 Ti PCI `05:00.0` and `0B:00.0`, and TP=2 as the other
rows. It regressed decode by 7.9 tok/s versus tile=4 with one warp, so the
experimental launch override was removed. The planned warp=4 service was
cancelled before it completed startup and was not benchmarked.

## Quality Probe

Prompt: `Explain why an index needs both a B-tree and a write-ahead log. Answer concisely.`

The original BF16 DFlash2 checkpoint with the SM75 transport produced a
semantically correct explanation of B-tree lookup/order and WAL durability/
crash recovery. It accepted 65/245 draft tokens (26.53%) on the default tile=2
route. This establishes that the 100% synthetic acceptance result must not be
generalized to normal text.

The tile=4 variant also produced a semantically correct answer and accepted
65/224 draft tokens (29.02%). Its GPU correctness subset passed 7 tests:

```text
tests/quantization/test_turboquant.py
  - single-token TQ roundtrip
  - raw verifier causal reference, with and without a prefix
  - raw verifier CUDA Graph capture safety
```

The rejected tile=4 stage-1 warp=2 probe also produced a semantically correct
answer. Its actual 21/96 request accepted 62/231 draft tokens (26.84%), with
prefill 110.7 tok/s, decode 85.2 tok/s, and E2E 89.6 tok/s on the same two
physical RTX 2080 Ti GPUs. These short-request rates are a quality probe, not
the 4K/128 throughput metric.

## Rejected Variants

- `deepsweet/Qwen3.8-27B-DFlash2-FP16`: on the same 4K/128 synthetic request,
  accepted 0/833 tokens and reached only 22.8 decode tok/s. Its conversion is
  not suitable for this SM75 target/draft pair.
- `VLLM_SM75_SPEC_SYNC_MODE=nosync`: four timed runs reached 187.0 decode
  tok/s, effectively identical to the safe route. It adds synchronization risk
  without a performance benefit.
- A fused B=8 TQ prefix decode (`VLLM_TURBOQUANT_CUDAGRAPH_SPEC_PREFIX_ROWS=0`)
  failed during FULL CUDA Graph capture with an illegal memory access in
  `custom_all_reduce.cuh:164`. The stable B=1 x 8 prefix topology must remain.
- `VLLM_TURBOQUANT_MAX_KV_SPLITS=8` did not improve decode throughput.
- TQ stage-1 `num_warps=2` reduced the 4K/128 isolated decode rate from 190.8
  to 182.9 tok/s. The launch override was removed; warp=4 was not benchmarked.

## Long-Context Capacity Fix

The initial 256K launch allocated the same physical block capacity to every
target, Mamba, and DFlash draft group. The five small FP16 draft pools then
consumed target-sized reservations, leaving an estimated maximum model length
of only 129,600 tokens. Native DFlash2 now plans a separate capacity per group
and keeps each group's block IDs independent. The profile also uses
`GPU_UTIL=0.90` to leave runtime workspace headroom for TurboQuant prefill.

Validation on `192.168.1.31`, TP=2, GPUs 1 and 5:

- Startup: `GPU KV cache size: 376,026 tokens`, maximum concurrency `1.43x`
  for a 262,144-token request.
- A 200,001-token prompt completed successfully with HTTP 200 in 260.19 s.
- A normal text probe returned a coherent answer and exercised DFlash2
  speculation (15 accepted draft tokens, 23.8% draft acceptance rate).
- Focused tests passed: 4 DFlash KV-cache tests, 16 DFlash2 spec-decode tests,
  4 KV connector zeroing tests, and 7 GPU model-runner tests.

## Fast 270K Profile Recheck

The promoted launcher route is
`2x2080Ti/qwen27b/w4a16/fast/dflash2-tqk8v4-2x172k-text-only.env`. It uses
`BLHNC` for mixed target/draft pages, prefix caching with Mamba `align`, and
`VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` for the 270,336-token experimental override.
It must be started through `launcher.sh --mode fast`; this selects non-eager
full and piecewise CUDA Graphs, safe SM75 synchronization, and the DFlash2
seven-token graph.

The launcher startup on `192.168.1.31` completed its health check and smoke
test. It reported `GPU KV cache size: 369,030 tokens` and
`Maximum concurrency ... 1.37x` for 270,336 tokens. A warmed streamed 4K/128
request measured approximately 1,400 prefill tok/s and 206 decode tok/s. A
quality probe returned a coherent B-tree/WAL explanation with 128 tokens.
The first request can JIT rejection/TQ kernels; benchmark results exclude that
warmup. A 32K request also completed with HTTP 200.
